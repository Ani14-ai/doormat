# DoorMate 0.3 — research checkpoint

**Status: source implementation and core simulations only. No 0.3 APK has been built, installed, or phone-tested.**

This is a replacement architecture for the earlier 0.2 prototype, not an APK rename. It removes the intent classifier and phrase-calibration flow. Do not reinstall 0.2 to test these changes: they are not in that APK.

## Intended experience

1. Download and load a local conversational AI model once.
2. Add approved caller numbers, each with its own instructions.
3. Practice a conversation, or run the built-in delivery scenario.
4. Complete the extra Shizuku/Samsung phone connection setup.
5. Enable experimental automatic calls and verify with a trusted caller.

The three screens are Assistant, Practice, and Setup. Delivery is an initial use case, not a hardcoded classifier category. Each caller can have different instructions for delivery, visitors, or another bounded scenario. No caller gets another caller's conversation history.

## Implemented in source

- Exact normalized caller-number allowlist; Indian local mobile numbers normalize to +91.
- Per-number free-text instructions, editable and removable. Editing pauses automatic calls.
- Practice chat: typed messages, optional phone speech-provider input, Android TTS replies, new conversation, measured response time.
- Built-in five-turn delivery simulation using the actual local-model adapter on-device. The caller prompts are scripted; assistant answers are generated by the model. This runner has NOT been executed here.
- Qwen 2.5 1.5B quantized local model through Google's LiteRT-LM 0.18.0 Kotlin API. No paid inference API, server or API key.
- One-time approximately 1.6 GB model download with published SHA-256 validation and a pinned repository revision.
- Shared conversation core for practice and calls: owner instructions plus the three most recent completed turns, short replies, AI identity on the first turn, credential-request guard, stale-result rejection.
- Android call-screening callback authorizes selected incoming numbers only; it does not reject any call or hide call notifications.
- Shizuku bridge drives exact Samsung Call assist / Call screening / Text call labels, then uses structurally distinguishable incoming messages and the send field.
- No manually spoken calibration phrases. **This is not universal compatibility:** layouts without explicit recognizable message-role IDs are unsupported and stop.
- Stops after 12 replies or three minutes; discards replies generated after hangup, pause, session replacement or a 20-second generation latency budget. Native inference itself may finish later; the 20-second limit is a discard rule, not a hard native cancellation guarantee.
- Visible stop notification; no reboot auto-enable or lock-screen changes.
- Structural diagnostic IDs and device version, without transcript text. Latest successfully submitted reply is stored locally; practice history is memory-only.

## Build when dependencies are reachable

Requirements: JDK 17, Gradle 8.11.1, Android SDK platform 35. The Gradle build resolves the pinned Android, Kotlin, Shizuku and LiteRT-LM dependencies.

```sh
gradle --no-daemon :app:assembleDebug
```

Expected output: `app/build/outputs/apk/debug/app-debug.apk`.

The included GitHub Actions workflow performs core tests and assembles a debug APK in an authorized repository. It has not been executed or published. No Gradle wrapper binary is included; use a Gradle 8.11.1 installation. The debug key is for testing, not a production release identity. Compile/API integration errors remain possible until this build runs.

Core tests need only JDK 17:

```sh
bash tools/test-core.sh
java tools/SyntaxCheck.java app/src/main/java
```

## Device test procedure after a successful build

1. Keep Play Protect enabled. If installation is blocked, stop and report the warning. No app name or signing configuration guarantees acceptance.
2. Open Setup, download the model over Wi-Fi, then load it. Leave the app open during the initial download. A failed download currently restarts, rather than resumes.
3. Open Practice. Start with the fictional example; run the delivery scenario and inspect exact address, gate, floor and refusal behavior. Try your own follow-up questions. Time and quality on this S24 are unmeasured.
4. Add a trusted test number and real instructions only when desired. Do not store access credentials in instructions. Ask questions not covered by instructions to check that the model asks rather than invents.
5. For calls, start Shizuku through wireless debugging, authorize DoorMate, allow phone/contact/notification permissions, select DoorMate for call screening, and check the bridge.
6. Enable experimental calls; have the approved test number call while the S24 is unlocked. Verify what the caller actually hears. A UI send action is not proof of delivered speech.
7. Check another, unapproved number rings normally. Test pause, hangup during generation, manual takeover, a second incoming call, and a subsequent new caller.
8. Repeat with the screen locked. If Samsung hides controls, no attempt is made to unlock the device. Treat locked-screen failure as a release blocker for unattended use.
9. If controls cannot be parsed, share the structural diagnostic. The fixture IDs in unit tests are synthetic, not observed IDs from the user's phone.

## Honest limits

- The requested install-and-normal-permissions-only experience is not achieved. Shizuku requires developer setup and a restart after device reboot.
- Samsung supplies call transcription and the spoken voice. This architecture does not offer arbitrary voice cloning, guaranteed interruption handling, or guaranteed human-like timing.
- A 1.5B model is not equivalent to a large cloud assistant. Incorrect facts, misunderstood instructions, prompt injection, or weak Hindi/Hinglish handling remain possible. Prompt instructions and simple credential guards are not a guarantee of correctness.
- The model has a 4096-token context, with bounded recent history. Long or token-heavy inputs may be rejected by the engine. The app stops rather than silently switching to fixed canned delivery answers.
- Selecting DoorMate for Android's screening role may interact with Samsung's own screening feature; this requires device verification.
- Caller ID is not authentication. This prototype is for ordinary delivery guidance, not sensitive information or identity-dependent actions.
- No internet inference is implemented. Internet permission is used by the model downloader. Optional speech input invokes the user's phone speech provider, which may use a network service. TTS behavior depends on installed voice settings.
- This source has not received an Android compilation, device installation, native-library compatibility/16 KB page-size check, or full security audit. It is a development checkpoint, not a release.
